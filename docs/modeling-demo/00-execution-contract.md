# 00 | Execution Contract and Scope

English | [中文](00-execution-contract.zh.md)

Version: 1.0 · Date: 2026-09-20 · Executor: Codex · Goal: Complete a demonstrable Demo in approximately two days.

## 0.1 Product Objectives

Develop a conversational data modeling workspace for data analysts/modelers, referencing the information architecture and interaction patterns from the provided Model X screenshot but utilizing our own product name, brand colors, components, and codebase. The provisional product name is "Smart Modeling Workspace" (智模工作台), which can be renamed via configuration.

Minimum Viable Loop: Upload CSV → Data Overview → Conversation-driven Plan Generation → User Modification/Confirmation → Cleaning & Feature Engineering → Optional Binary Classification Training → Download Real Results & Artifacts.

Core Experience Layout: "Left Panel for Sessions and Navigation — Center for Conversations and Business Cards — Right Panel for Tasks and Context." This is not a promotional website, generic admin dashboard, or Notebook clone.

## 0.2 Immutable Constraints

- Base: `deepseek-ai/deepseek-harness`. Retain existing sessions, Agents, model adapters, tools, Web communication, and plugin lifecycles.
- Frontend: Continue using the existing React / Slots / Client Model architecture; do not build a new Next.js or Vite application to replace Harness, nor rewrite the Agent Loop.
- Branding: Primary color fixed at `#0F4C9E`. Expanded menus use icons + Chinese text; all actionable buttons include an icon, with primary business buttons retaining both icon and text. Compact tool buttons may be icon-only but must have a Tooltip and accessible name.
- Runtime Deployment: Must support intranet deployment only. Do not automatically call public LLMs, external MCP servers, online fonts, or CDNs; isolate development tool network access from product runtime execution.
- Computation & Safety: Compute in Python. The LLM is restricted to planning, explanation, and selecting whitelisted tools. It must NOT execute freely generated Python/SQL/Shell code or install dynamic dependencies.
- Human-in-the-loop: Write tasks for cleaning/features/training can only start after real human confirmation. Models cannot forge approval; frontend "Confirmed" status does not serve as backend authorization basis.
- Metrics Integrity: Task statuses, metrics, and artifacts must be generated by the executor. Prohibit `setTimeout` to fake completion, hardcoding AUC values, or disguising offline replay as real-time computation.
- Scope Boundaries: Support custom project business Skills and editable workflows; the two-day Demo implements bounded features below without claiming a full arbitrary DAG platform capability.

## 0.3 P0 Demo & Subsequent P1 Enhancements

| Item | P0: Two-Day Acceptance | P1: Future Enhancement |
|---|---|---|
| Data Input | Single CSV, single wide table; explicit encoding/size limits | XLSX, multi-table, database, optimized chunked upload with breakpoints |
| Data Prep | Overview, missing check, type check, whitelist cleaning/coding, training data output | Complex transaction window aggregation, automatic feature search |
| Modeling | Labeled binary classification, single true logistic regression pipeline | Random Forest/XGBoost, hyperparameter tuning, model serving |
| Workflow | Fixed skeleton, node parameter editing, optional feature on/off, constrained re-run | React Flow arbitrary DAGs, branching/loops/concurrency |
| Skill | 4 Business Skills; body text edit, save draft, validate, publish snapshot | Batch import, full evaluation suite, canary release, auto-optimization |
| Interface | Three-column workspace, data drawer, lightweight Skill management panel | Scenario lab, Notebook, complete resource portal |
| Storage | SQLite + local files; reuse existing storage if available | PostgreSQL / RustFS for full productization |
| Execution | Single compute task concurrency, independent subprocesses, timeout cancellation, refresh recovery | Distributed queues, training checkpoint restoration, multi-tenancy |

Three distinct delivery levels must be separately defined:

1.  **UI Integration Pass**: Static/fixture component states are visible; this cannot count as business acceptance.
2.  **Real Loop Pass**: At least one synthetic dataset with real LLM planning, human confirmation, computation, and download completion.
3.  **Scale Validation Pass**: Read, analyze, clean, basic feature engineering, and export on specified million-row × hundred-column data must include timing/peak memory records. Small sample results cannot substitute; training capability for millions of rows cannot be auto-inferred without actual testing.

Recommended main demo dataset size: 5,000 ~ 50,000 rows, 10 ~ 50 columns; increase to 100,000 rows if resources permit. Million-row tests are independent capacity validation tasks; incomplete results must be honestly labeled without blocking the small-data Demo, but cannot claim full initial capacity acceptance is met.

## 0.4 Execution Principles

First check repository and environment at T00. Complete fixed compute pipelines not dependent on LLM first, then integrate Agents, finally refine UI. Ensure every step remains runnable; do not write large amounts of empty pages upfront.

Use an estimated budget of ~18 hours + 2 hour buffer for tasks only; this is estimation, not a performance/delivery guarantee. If source builds, intranet models, or environment permissions block progress, record real failures and scale back P1; never silently swap the base model or fill with fake results.

## 0.5 Codex Output per Stage

At end of each stage, write to `docs/modeling-demo/progress.md`: Task ID, modified files, run commands, exit codes, screenshot/log paths, remaining issues, and next task. Checks not executed must be marked `NOT_RUN`; do not mark them as "Passed".

Allow continuous implementation within scope but do not auto-push, send PRs, modify global permissions, install unknown plugins, or delete user code without authorization. If fundamental architecture conflicts are discovered, record in DECISIONS and report; never re-architect the system unilaterally.

## 0.6 True Business Boundaries

This tool is a R&D Demo and does not handle real credit granting/fraud prevention decisions. All page data and tests use synthetic or approved anonymized data. Numbers from reference screenshots are for visual guidance only, serving as neither training data nor performance evidence or product capability commitments.
