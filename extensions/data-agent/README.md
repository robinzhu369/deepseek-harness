# Data Agent execution foundation

English | [中文](README.zh.md)

This private extension provides validated DAGs, PostgreSQL workflow revisions and approvals, durable attempt leases, cancellation, candidate publication, event cursors, an authenticated internal Worker HTTP host mounted through a dsh source profile, a remote HTTP Worker supervisor with Docker isolation, multipart uploads and immutable imports, and controlled Skill versions. The [task ledger](../../implementation/tasks.md) tracks the complete product scope and outstanding work.

## Development

From the Harness root, run `pnpm install --frozen-lockfile`, then `npm --prefix extensions/data-agent run typecheck` and `npm --prefix extensions/data-agent test`. The extension belongs to the root pnpm workspace and lockfile. Type checking builds the referenced Cordis project and resolves its source through project references. Configure `DATA_AGENT_TEST_DATABASE_URL` for a disposable PostgreSQL 16 database whose name ends in `_test`; the suite truncates only its `data_agent` tables. The default targets loopback port 55439 and the synthetic `data_agent_test` database. `DATA_AGENT_TEST_PYTHON` optionally selects an absolute Python path with the Worker requirements installed.

From the Harness root, run `PYTHONPATH=services/data-worker python3 -m pytest services/data-worker/tests -q`. Generate the shared JSON schemas with `node --import ./node_modules/tsx/dist/loader.mjs extensions/data-agent/scripts/export-contracts.ts`.

## Runtime rules

`DataAgentService` requires a Pool, explicit lease/retry/concurrency settings, and an object verification callback. Trusted adapters supply project/member and worker identities. The Python process receives only resolved attempt inputs and an isolated output prefix; it receives no database credentials or inherited application secrets. A source `.py` executor is invoked only by the host adapter; it is not a standalone Node application launcher.

Workflow edits use expected revisions. Submission freezes the current version and approval digest. Draft layout does not affect computation identity. External references require project membership and published digests; internal references resolve only after upstream publication. Result receipts are idempotent by attempt and manifest digest. Publication and per-run event cursors share a transaction. Waiting candidates release their lease. Cancellation remains requested until executor exit is acknowledged.

`createWorkerHandler` mounts POST routes under `/v1/worker`: acquire, heartbeat, progress, submit, failure and cancelled. Configure service-account credential SHA-256 digests and project allowlists on the host. Acquisition returns a random attempt credential; only its hash is stored. Service credentials cannot submit results, and attempt credentials cannot acquire work or change their identity. Apply migrations 001–008 before mounting the handler. The handler itself does not listen; the Cordis host owns its listener. Authenticated input downloads and bounded output uploads transfer bytes without shared Worker storage. Remote connections require a separately configured internal TLS proxy.

## Source-profile host

Copy [profile.package.json](../../deploy/data-agent/profile.package.json) to a new `$DSH_HOME/profiles/data-agent-worker-host/package.json` and create an empty `cordis.patch.yml` containing `[]` beside it. Configure `DATA_AGENT_HOST_CONFIG` with the JSON fields in [host.config.example.json](../../deploy/data-agent/host.config.example.json); replace all placeholders and create the absolute storage directory. Set the database credential in the variable named by `database_env` and apply migrations 001–008 to that database before launch. From the Harness root, run `pnpm dsh --profile data-agent-worker-host --patch deploy/data-agent/cordis.source.patch.yml`.

The source overlay mounts the console exporter and domain host over an empty profile. It binds only to loopback and checks the exact Host allowlist; a separately configured internal TLS reverse proxy is required for remote access. Pool size, database/request timeouts, shutdown grace, job limits and recovery interval are explicit configuration fields. Recovery is serialized. SIGTERM closes the listener, interrupts stalled connections after the grace period, waits for active handlers and recovery, and then closes the pool. An incompatible schema or failed initialization aborts startup; it never migrates automatically. The dsh process supervisor enforces a five-second overall exit budget, so configure host timeouts within it; a forced exit leaves unfinished attempts subject to durable lease recovery.

This profile hosts Worker and user-account-authenticated `/v1/data` routes. Configure user credential hashes separately from Worker accounts; PostgreSQL membership controls read, write and owner-only release permissions. Empty `user_accounts` disables user access. The optional Harness overlay provides real agent sessions, scoped domain tools and a locked Skill Provider; enterprise identity and browser UI remain separate integration work. There is no separate invariant installer because this adapter owns no independent service projection; publication checks remain in the domain service and object verifier.

## Remote Worker

Build the compute image with `docker build --pull=false -f deploy/data-agent/Worker.Dockerfile -t data-agent-worker:dev .`. The Dockerfile pins the Python base digest and runtime package versions; this development build requires package downloads and is not offline-delivery evidence. Use the immutable image ID from `docker image inspect data-agent-worker:dev --format '{{.Id}}'` in [remote.config.example.json](../../deploy/data-agent/remote.config.example.json). Configure an absolute Docker executable, its home directory, a private persistent supervisor root, explicit byte/time/CPU/memory/PID budgets, and the environment variable containing the service credential. Run `python3 services/data-worker/remote.py --config /absolute/remote.json`; `--once` processes at most one new attempt.

Only the supervisor receives service and attempt credentials. Each compute container uses no network, a read-only root, no capabilities, no privilege escalation, UID 65532, read-only downloaded inputs, and quota-bound temporary/output mounts. The supervisor verifies input/output SHA-256 values and exact byte counts. Heartbeats span transfers and computation. Cancellation acknowledgement follows confirmed container exit; restart recovery stops the journaled container before replaying its receipt or reporting interruption. The persistent private journal contains an attempt credential and must be protected with the supervisor root. A compute deadline inside the container also bounds execution after supervisor failure. This Docker backend targets Linux containers and a POSIX supervisor with `fcntl`.

Set `DATA_AGENT_TEST_IMAGE` to the compute image ID to enable the real HTTP/Docker integration cases. Build `services/data-worker/tests/fixtures/Dockerfile` with `--build-arg WORKER_IMAGE=data-agent-worker:dev` and set `DATA_AGENT_ISOLATION_IMAGE` to that fixture image ID for kernel-isolation, cancellation and restart cases. Missing image variables skip these cases explicitly; the recorded validation supplies both.

## Data center and Skill lifecycle

Data routes provide project creation/listing, scoped multipart grants, resumable part metadata, whole-file SHA-256 completion, immutable import versions, dataset search/pagination, queued column/row previews, archive protection and Range downloads. Parse options and roles define a new import identity; identical requests reuse it. Import and preview execute through the Worker queue. API imports reject quarantine options until the approval adapter exists. Failed uploads can retry while live. Expired unfinished uploads become aborted; cleanup waits for the configured grace and refuses prefixes referenced by artifacts. Discard only tombstones unreferenced, unarchived artifacts; historical run outputs retain their bytes.

Skill drafts use optimistic revisions; candidates freeze the full package digest. A server-owned evaluator must cover the configured planning/frozen lanes and regression/holdout cases with no blocking failures before owner-only publication. Evaluation evidence binds the package, suite and runtime digests. Publication does not change the default version. Default selection supports rollback to a released version; retirement blocks new invocations while existing invocation IDs load their locked snapshots. Feedback records reference those invocations. HTTP callers cannot supply evaluation reports. The optional `quality_evaluation` configuration enables synthetic baseline/candidate comparisons on real Harness Agents plus deterministic Python oracles. Evaluation sessions replace the ambient coding prompt and expose only the result-submission tool. Valid proposed DAGs execute through the Worker engine; independent row comparisons check original values, identifiers, targets and calculated outputs. Frozen computation remains a separate lane. Execution traces retain failures without retrying failed model responses. Use [quality.config.example.json](../../deploy/data-agent/quality.config.example.json) to configure repetitions (at least three), timeouts, Python executable, byte budgets and concurrency; place the object in the host’s `quality_evaluation` field. The Python environment must contain Worker requirements. HTTP timeouts must accommodate the complete repeated suite. Each input, complete package, tool call and response is logged in JSONL. Reports retain repeated outcomes, failure frequency, variance and session IDs; unknown monetary cost is null. These suites cannot authorize business publication: `BUSINESS_EVALUATION_REQUIRED` remains until a server-owned, human-reviewed suite is available. The Harness adapter loads only explicitly selected released versions; business-labelled evaluation remains required for release.

## Harness sessions

Apply migrations 001–008. Set the host's `harness` field using [harness.config.example.json](../../deploy/data-agent/harness.config.example.json), and set `DATA_AGENT_SESSION_ROOT` to a private persistent directory. Add `--patch deploy/data-agent/harness.source.patch.yml` after the Worker-host source patch on the same `dsh --profile data-agent-worker-host` launch. The overlay composes the existing Agent loop, JSONL persistence, tool registry, Skill registry and official DeepSeek adapter. Set `DEEPSEEK_BASE_URL` explicitly and supply `DEEPSEEK_API_KEY` through the process environment. The tested public endpoint is `https://api.deepseek.com`, using `deepseek-v4-flash`; the connection probe reports the server model label `deepseek-flash`. Public-endpoint tests send synthetic data only.

Authenticated `POST /v1/data/:project/sessions` accepts `{input, skills: [{id, version}]}`; `input` follows the shared Skill input schema, and a null version selects the current released default. The server generates the session ID and freezes its authenticated actor, project, dataset, policy, runtime and invocation IDs in PostgreSQL. Scope setup finishes before the Agent becomes visible. Input context, frozen workflow defaults, complete proposal/operator schemas and tool calls/results enter the ordinary Harness Session log. The model cannot choose a session owner through tool arguments. PostgreSQL membership and session ownership are checked on every call.

`POST .../sessions/:id/messages` accepts `{text}` and waits for the real turn to become idle; concurrent messages are rejected with `SESSION_BUSY`. Configure the HTTP timeout for expected model latency. `POST .../:id/cancel` cancels the conversation; data Runs retain their own cancellation protocol. After process restart, `POST .../:id/resume` loads the JSONL history and the original invocation locks, including versions retired since that session was created. Disposal rejects new work, cancels live turns, drains handlers and flushes/disposes Agent handles before the pool closes.

The scoped tools are `skill`, `read_skill_resource`, `inspect_dataset`, `propose_workflow_patch`, `get_run_snapshot` and `read_report`. The first two load only locked packages and resources. Diagnostics return a submitted Run; reports become readable only after Worker publication. The proposal tool accepts `proposal_json` with the shared proposal fields except session identity, which the server supplies; saving cannot approve or execute. Run/report reads require session ownership, including published outputs reused by that session. Global shell and unrelated tools are excluded. No tool can grant approval or publish a Skill. Initial context and results have configured byte limits. Complete task chains, approval UI and model-driven full Skill evaluation are not established by the real-model diagnostic-submission smoke.

## Unified proposals and decisions

`POST /v1/data/:project/proposals` accepts the strict `PlanProposal` envelope: workflow ID, expected revision, optional session identity as null, goal, workflow, published evidence and its input/sampling scope, expected impact per sensitive node, and unmet prerequisites. Conversation and product clients use the same revision transaction. The response includes immutable input versions, parameter digests, confirmation items and before/after node differences. Evidence must match the proposed inputs; known protected roles are checked before a draft is saved. `GET .../proposals/:id` returns the envelope, decision history and stale status.

Authenticated `POST .../proposals/:id/decision` accepts approve/reject, the exact proposal digest and a reason; approval also requires the per-node full-computation limit `max_removed_fraction`. Unmet prerequisites prevent approval. `POST .../:id/submit` accepts an idempotency key and freezes the approved current revision. Changed inputs or parameters require a new decision; exact prior Run retries retain their receipt. `GET .../runs/:run/candidates/:job` exposes actual impact and output metadata without unpublished object paths. Its `/decision` route binds approve/reject to the manifest digest and reason. Approval rechecks object checksums, current workflow and cancellation; rejection retains diagnostics and stops descendants. Browser approval cards remain separate work.

## Business tasks and reruns

Apply only unapplied migrations in numeric order through 008; do not replay an older migration over a newer schema. Task submissions require the host's configured Harness runtime. `POST /v1/data/:project/tasks` accepts a name, goal, published full DatasetRef and idempotency key. This completes the upload phase. `/tasks/:id/submit` accepts the strict [TaskRun](src/task-contracts.ts) fields: approved proposal, analysis/processing/features stage, predecessor, optional source Run, execution scope, reuse flag, explicit selection flag, expected task revision and idempotency key. Predecessors must belong to this task and have completed their selected work; advancing stages also requires a published report or dataset. Inputs must belong to the root dataset or predecessor lineage. One stage can contain several Runs.

`GET .../tasks/:id` returns the selected lineage, branches, phase Run statuses and final export references. `/follow` returns a complete replacement snapshot and a cursor vector; pass its JSON-encoded `cursor` query parameter on reconnect to obtain `changed`. Run cursors and the task revision are read from one PostgreSQL snapshot. `/select` requires a Run ID and expected revision. Branch creation never changes selection unless `select` is explicitly true. A successful phase Run does not complete the task: the selected chain must cover all stages and end with a published `export` bundle that passes the training contract. The Worker checks partition identity, schemas, protected roles, transformer consistency, overlap and quality before publishing the ZIP, its manifest and frozen recipe.

`POST .../runs/:id/rerun` freezes the original plan, inputs, dependency graph and Skill locks without invoking a Skill. Runtime or policy incompatibility refuses replay. Editing a plan or selecting another Skill requires a new proposal and approval. `scope` is `{kind:"all"}`, `{kind:"through",node_id}` or `{kind:"from",node_id}`. Through selects the node and ancestors; from forces the node and descendants and includes their prerequisite closure. Other nodes remain `not_selected` and do not affect Run status. A through-node Run cannot establish a completed business phase.

Reuse is explicit and limited to the source Run. Persisted computation keys include input versions, checksums, schema/role/transformer/split metadata, operator version, parameters, seed, environment and policy. Skill text is excluded. Deployment changes to operator code or resource/quality policy must change their environment or policy digest. Unchanged nodes reuse original ArtifactVersions only after authorization, approval-impact checks and fresh input/output byte verification. Missing, corrupt or incompatible objects cause recomputation. Old jobs without computation keys cannot hit the cache. Export reuse retains the original recipe and producer identity; a changed workflow requires a new export. No process-local cache owns task state.

`POST .../runs/:id/pause` and `/resume` stop or enable acquisition at node boundaries; an active attempt may finish while scheduling is paused. `/runs/:id/cancel` affects only that Run. `/tasks/:id/cancel` stops future submissions and cancels active branches while retaining published outputs. Cancellation stays requested until running executors acknowledge exit. Sessions may supply `business_task_id`; the server validates the selected dataset lineage and logs the task context and schemas. These sessions additionally expose `get_task_snapshot`, `submit_task_run` and `rerun`, with session-bound proposals and replay sources. Human decision tools remain unavailable.

## Support and limitations

CSV fields remain strings unless a type is declared. Empty fields remain empty strings unless the explicit null markers include the empty string; declared nulls are applied before numeric conversion.

The Worker supports UTF-8/GB18030/UTF-16 CSV and Parquet import, explicit headers/null markers, approval-bound bad-record quarantine, decimal rounding/timezone policies, stable row IDs, exact diagnostics, random/entity/time/stratified splitting, train-only mean/median/mode/quantile-clipping/scaling/One-Hot fit and transform, constant fill, normalization, category maps, deterministic deduplication, restricted filters, fixed bounds, arithmetic/date/missing features, protected column selection, quality checks and Parquet bundles. Unsupported options and unknown operators fail explicitly. Quarantine preserves original record positions; malformed CSV syntax still fails because safe record recovery is unavailable. Memory processing is eager and bounded only by deployment resources; it is not a streaming guarantee.

This extension is a private pnpm workspace with a tested dsh source-profile host. The optional Web Remote adapter connects it to the workbench; it remains outside the upstream release build. The four source packages are candidates for synthetic model evaluation; they are not business-qualified or released Skill versions. Remaining operator coverage, enterprise identity, RustFS/S3 storage, internal TLS deployment, business-labelled Skill evaluation and offline delivery remain in the task ledger. Do not deploy this library as a completed application.

The [capacity probe](../../evals/data-agent/benchmark.py) measures deterministic compute only. It does not establish AC-43 or offline deployment acceptance. The [acceptance ledger](../../implementation/acceptance.json) retains all 54 requirements without marking component tests as product acceptance.

## Optional three-column Web workbench

Build Host and Client libraries, apply unapplied migrations through 008, and prepare the existing host configuration with its Harness runtime enabled. Launch the real Web profile with `pnpm dsh --profile web --patch deploy/data-agent/workbench.source.patch.yml`. `DATA_AGENT_DOMAIN_ENDPOINT` must equal the configured domain listener origin (for example `http://127.0.0.1:55440`). The overlay defaults to 2-second polling and a 64-MiB browser upload buffer limit. The host's upload/body limits still apply. Open the authenticated URL printed by dsh, then enter a separate domain user credential. Credentials remain in memory and are not copied into localStorage.

The sidebar owns project/session navigation and the data, Skill and template dialogs. The center renders actual Harness messages and tool results plus digest-bound proposal decisions. The right column switches between authoritative Run status and an editable React Flow draft; selecting history never changes its frozen workflow. Copying produces an independent workflow identity. Evidence JSON is required for protected changes and remains subject to backend validation. Skill stage entries create a new session with the selected immutable version, then request a proposal; an unreleased or retired candidate cannot bypass lifecycle checks. Domain sessions use their scoped data prompt and native domain tools, excluding ambient Web coding tools and runtime context.

Migration 008 adds session titles and revisioned templates. Read routes expose account identity, operator schemas, owner-scoped session navigation/history, immutable workflow/Skill versions and bounded JSON reports. Template writes use optimistic revisions. The Host Remote forwards bounded JSON and exact binary routes through the existing authenticated Web carrier; disposal aborts outstanding forwarding.

Local browser regression: set `DATA_AGENT_TEST_DATABASE_URL` to a disposable database whose name ends in `_test`, set `DATA_AGENT_BROWSER_CHANNEL=msedge` when using installed Edge (otherwise Playwright Chromium), and run `DSH_SNAPSHOT=replay pnpm exec vitest run --config vitest.web.config.ts extensions/data-agent/tests/workbench-browser.e2e.ts`. The fixture clears that test database. Only the external model is scripted; Loader, Agent, loop, tools, Remote, browser and PostgreSQL are real. This test does not certify Skill business quality, large-data capacity or offline deployment.

The [full-chain capacity report](../../implementation/t14-capacity.md) records a fixed million-row workload through the actual Web profile, remote Worker and training export. Its optional `DATA_AGENT_CAPACITY_CONFIG` fixture records resource limits, node measurements and independent full-row reconciliation. The local 4-GiB result does not certify wide tables, high-cardinality encoding, concurrent users or the target deployment.
